# Mundus website leads: delivery setup

All three public lead sources are persisted and routed to **mundus.languages@gmail.com**:
- Individual/group inquiries: `contact_requests` → `contact_request_email_outbox`.
- Company inquiries: `company_quote_requests` → `company_quote_email_outbox`.
- Consented newsletter signups: `newsletter_subscribers` → `newsletter_email_outbox` (`confirm` for subscriber; `admin_notice` for Mundus).

The backend worker is `GET /api/notifications/process` and requires a 32+ character bearer token and SMTP. In production, set these **server-only** environment variables in Vercel (do not prefix with `NEXT_PUBLIC_` or commit secret values):

| Key | Value |
| --- | --- |
| `MUNDUS_EMAIL_NOTIFICATIONS_ENABLED` | `true` |
| `MUNDUS_SMTP_HOST` | `smtp.gmail.com` (if using Gmail SMTP) |
| `MUNDUS_SMTP_PORT` | `465` (TLS) |
| `MUNDUS_SMTP_USER` | `mundus.languages@gmail.com` (if this Gmail account is the sender) |
| `MUNDUS_SMTP_PASSWORD` | A Gmail app password generated by the mailbox owner, or the SMTP password of an authorized provider |
| `MUNDUS_EMAIL_FROM` | `Mundus Languages <mundus.languages@gmail.com>` (if using Gmail SMTP) |
| `CRON_SECRET` or `MUNDUS_NOTIFICATION_SECRET` | Random secret, at least 32 characters (no reuse of service-role/Stripe secrets) |

**Scheduler required.** Send an authenticated `GET` request to `/api/notifications/process` on a recurring schedule using `Authorization: Bearer <secret>`. Use Vercel Cron where supported by the account plan, or a trusted external scheduler that supports a secret header. Do not add an unrestricted public endpoint. Daily cadence may be insufficient for fast lead response; a short interval is preferable if the hosting plan permits it. Redeploy once environment variables are added.

**Validation (must be done before calling inbox delivery live):**
1. From the deployed public site, submit one test contact inquiry, one company quote and one consenting newsletter signup, using distinct permitted test emails.
2. Verify all three rows exist in their respective Supabase tables and exactly one job per request in the matching outbox (newsletter requires its own confirmation and separate admin notice).
3. Run the authorized worker; confirm it returns `sent > 0` and jobs transition to `sent` with `sent_at`, not merely an HTTP 200.
4. Verify that the three notifications arrive at `mundus.languages@gmail.com` and the newsletter confirmation reaches the subscribing email, and that `Reply-To` is the lead email for contact/company requests.
5. Run the worker again and confirm no duplicate delivery; verify retry after a simulated SMTP failure.

**Current status at code review, 2026-11-08:** SMTP/scheduler secrets were absent from the Vercel production environment. Saving an inquiry in the dashboard is working in source, but actual email delivery **must not** be represented as active until those settings and inbox tests pass.
