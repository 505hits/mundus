Package balances are displayed per purchased package with total/used/remaining counts and a repeat-purchase link. Renewals use the same fixed catalog and verified Stripe order flow; consumed first-purchase discounts do not return. Existing schedule requests/approval and text homework remain in place. Apply 202610030004_learning_files.sql in the verified preview. It creates private mundus-learning bucket and metadata. A pre-existing public bucket with that ID blocks application. Students upload homework submissions; active assigned teachers upload material or homework assignments. PDF, PNG, JPG and UTF-8 TXT only, max 3 MB. Server checks signatures/size and assignment, then writes service-only metadata; cleanup attempted if metadata insertion fails. RLS governs file lists. Downloads reauthorize and use signed attachment URLs valid for 60 seconds; anyone possessing a still-valid signed link can use it. No public storage policy is created. Signature checks are not malware scanning. No delete UI or third-party scanning service added. Server action body limit 4 MB fits current hosted request limit with form overhead.

Apply 202610030005_schedule_email_outbox.sql after existing schedule-request integrity migrations. New requests queue pending notifications for verified active student and assigned teacher; accepted/declined transitions queue decisions. Changes do not email arbitrary form-entered recipients. Trigger and schedule update share a transaction; rollback does not queue mail. Unique request/recipient/event avoids duplicate queue insertion. Existing historic requests are not backfilled. Do not delete referenced request records while notifications are retained.

Delivery stays off by default. Configure an existing verified SMTP account using MUNDUS_SMTP_HOST, MUNDUS_SMTP_PORT (465 or 587), MUNDUS_SMTP_USER, MUNDUS_SMTP_PASSWORD and MUNDUS_EMAIL_FROM; credentials are server-only. SMTP must support TLS and the sender must be approved. Configure MUNDUS_NOTIFICATION_SECRET (>=32 random characters) or CRON_SECRET, and only enable MUNDUS_EMAIL_NOTIFICATIONS_ENABLED after preview tests. Auth email SMTP settings do not automatically supply these application variables.

Schedule authenticated GET/POST /api/notifications/process with Authorization: Bearer <secret> in the deployment's approved scheduler. No production cron or actual mail has been enabled here. Each call leases at most two jobs; repeat calls drain the queue, unsuccessful jobs retry after 15 minutes, five attempts maximum, stalled leases expire after 10 minutes. Exhausted stalled leases become failed. Delivery rechecks active verified recipient identity and links to student/teacher/admin schedule route. SMTP acceptance is not proof of inbox delivery. At-least-once delivery: a crash after SMTP acceptance but before recording sent can produce a duplicate, despite stable Message-ID. Worker returns counts, never recipient data or SMTP errors/secrets. Failed jobs need administrator inspection; no automatic bulk replay.

Apply 202610030006_notification_recovery.sql for skipped status and restricted retry RPC. Before sending, worker rechecks request status/time and current lesson recipients; outdated jobs are marked skipped. This is a last-moment check, not a lock across SMTP delivery, so a concurrent request change can still race with sending. Admin can requeue individual failed jobs; database verifies current event/time and active verified recipient, and rejects already queued/sent or obsolete jobs. No bulk resend. Admin warning explains duplicate SMTP delivery possibility. No notification sent during development.
